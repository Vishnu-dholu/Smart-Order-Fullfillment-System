\section{System Overview}
\subsection{User Roles}
The Smart Order Fulfillment System handles multiple user roles to ensure robust access control and specialized dashboards:
\begin{itemize}
    \item \textbf{Customer:} Can browse products, place orders, view order history, and receive delivery notifications.
    \item \textbf{Admin/System Operator:} Can monitor system health, oversee inventory levels, view aggregate order data, and manage delivery personnel assignment.
\end{itemize}

\subsection{Core Functionalities}
The system automates the entire lifecycle of an e-commerce order:
\begin{itemize}
    \item \textbf{Order Placement:} Securely processing incoming purchase requests.
    \item \textbf{Inventory Management:} Real-time deduction of stock levels to prevent overselling.
    \item \textbf{Warehouse Routing:} Geographically calculating the optimal warehouse to fulfill an order based on customer location.
    \item \textbf{Delivery Dispatch:} Assigning personnel and tracking shipment status.
    \item \textbf{User Authentication:} Secure login and Google OAuth integration using JWTs.
\end{itemize}

\subsection{Microservices-Based Design}
The system is built on a highly decoupled, polyglot microservices architecture. It strictly adheres to the principle of "one database per service" to ensure data sovereignty. The core transactional domains are written in Java (Spring Boot) for reliability, while computationally heavy or asynchronous tasks are offloaded to Go (Fiber) services for maximum throughput and minimal memory footprint.

\subsection{High-Level Request Flow}
\begin{enumerate}
    \item A client application sends an HTTP request.
    \item The request hits the Nginx Ingress Controller deployed on the Kubernetes cluster.
    \item The Ingress Controller routes the request to either the React Frontend or the API Gateway.
    \item The API Gateway validates the JWT, handles CORS, and proxies the request to the appropriate internal microservice.
    \item The microservice processes the request, interacting with its dedicated PostgreSQL database, and potentially communicating synchronously or asynchronously with other services before returning the response.
\end{enumerate}

\section{Overall System Architecture}

\subsection{Architectural Style}
The project employs a polyglot microservices architectural pattern. This allows independent scaling, deployment, and technology selection for distinct business domains.

\subsection{Frontend Architecture}
The frontend is a Single Page Application (SPA) designed using React and Vite. It utilizes Tailwind CSS for utility-first styling and React Router DOM for client-side navigation. The UI communicates strictly with the API Gateway.

\subsection{Backend Microservices Architecture}
The backend is logically divided into two language ecosystems:
\begin{itemize}
    \item \textbf{Spring Boot Ecosystem (Java):} API Gateway, Auth Service, Inventory Service, Order Service.
    \item \textbf{Go Ecosystem (Fiber):} Warehouse Service, Delivery Service, Notification Service.
\end{itemize}

\subsection{Database Architecture}
A decentralized data management pattern is implemented. Every microservice has its own isolated PostgreSQL database schema. This prevents tight coupling at the data layer and avoids a single point of failure.

\subsection{Inter-Service Communication}
Internal services communicate primarily via RESTful HTTP calls over the internal Kubernetes network (\texttt{ClusterIP}). Authentication for inter-service communication is handled via internal service tokens to bypass standard user JWT validation.

\subsection{Deployment Architecture}
The entire application runs inside a Kubernetes cluster (Minikube for local/dev). All services are containerized using Docker. Deployment state is managed declaratively via Ansible and applied as Kustomize manifests.

\subsection{Observability Architecture}
The project migrated from ELK to the PLG (Prometheus, Loki, Grafana) stack for high-efficiency monitoring. Prometheus scrapes metrics, Promtail tails logs and ships them to Loki, and Grafana visualizes the unified data.

\subsection{Security Architecture}
Security is multi-layered:
\begin{itemize}
    \item \textbf{Edge:} Nginx Ingress Controller.
    \item \textbf{Perimeter:} Spring Cloud Gateway validates all incoming JWTs.
    \item \textbf{Secret Management:} Ansible Vault dynamically injects secrets at deployment time, keeping them out of version control and Kubernetes ConfigMaps.
\end{itemize}

\section{Frontend Architecture and Implementation}

\subsection{Frontend Architecture Overview}
The frontend leverages a component-based architecture using React. The Vite build system provides sub-second hot module replacement during development and aggressive tree-shaking during production builds.

\subsection{Communication with Backend}
All HTTP requests are orchestrated using Axios. A global Axios interceptor is configured to automatically attach the user's JWT (stored securely) to the \texttt{Authorization} header of every outbound request targeting the API Gateway.

\subsection{User Interface Flow}
The UI is divided into public routes (Login, Register) and protected routes (Dashboard, Order History). React Router handles the transition between these views seamlessly without page reloads.

\subsection{Authentication Handling}
Authentication state is managed by decoding the JWT payload locally. Upon a 401 Unauthorized response from the API Gateway, the application automatically clears local session data and redirects the user to the login screen.

\subsection{Frontend Deployment}
The frontend is built via a multi-stage Dockerfile. The first stage uses Node.js to compile the Vite project into static HTML/CSS/JS assets. The second stage serves these assets using a lightweight Nginx container, drastically reducing the final image size.

\section{Backend Architecture and Implementation}

\subsection{Backend Design Principles}
The backend enforces strict bounded contexts. The Order service, for example, knows nothing about the internal database schema of the Inventory service.

\subsection{Backend Service Composition}
\begin{itemize}
    \item \textbf{Transactional Core:} Spring Boot handles complex state machines, ACID transactions, and complex object-relational mapping (Hibernate).
    \item \textbf{High-Throughput Edge:} Go handles tasks like geographical distance calculations (Warehouse routing) and asynchronous I/O (SMTP email dispatch) where CPU and memory efficiency is paramount.
\end{itemize}

\subsection{Synchronous Service Communication}
When immediate consistency is required (e.g., checking if inventory exists before confirming an order), services communicate synchronously over HTTP. The Kubernetes internal DNS (\texttt{service-name.namespace.svc.cluster.local}) is used for service discovery.

\section{API Gateway}

\subsection{Role of the API Gateway}
The API Gateway acts as a reverse proxy and the single point of entry into the internal network. It abstracts the complexity of the microservices architecture from the frontend.

\subsection{Routing Mechanism}
Using Spring Cloud Gateway, incoming requests are routed based on path predicates (e.g., \texttt{/api/v1/orders/**} maps to the \texttt{order-service}).

\subsection{Security and CORS}
The gateway centralizes Cross-Origin Resource Sharing (CORS) configurations and performs global JWT validation. If a token is invalid or expired, the request is dropped before it ever consumes resources on the downstream microservices.

\section{Auth Service}

\subsection{Core Responsibilities}
The Auth Service manages user registration, credential verification, and token issuance.

\subsection{JWT-Based Security}
Upon successful login, the service generates a signed JSON Web Token. The signature is created using a highly secure, base64-encoded secret stored in Ansible Vault.

\subsection{Google OAuth 2.0 Integration}
The system supports social login. The frontend receives an OAuth token from Google, which the Auth Service securely verifies against Google's public key endpoints before issuing an internal JWT.

\subsection{Database Design}
The Auth PostgreSQL database simply maps UUIDs to email addresses, encrypted passwords, and role designations.

\section{Core Business Services}

\subsection{Order Service}
Responsible for maintaining the canonical state of a customer's purchase. It orchestrates the flow: validating the user, verifying inventory, confirming the warehouse, and dispatching delivery instructions.

\subsection{Inventory Service}
Manages stock levels. It implements robust database-level locking and transaction isolation to prevent race conditions (e.g., two users purchasing the last item simultaneously) during high concurrency spikes.

\section{Go Microservices Ecosystem}

\subsection{Warehouse Service}
Written in Go using Fiber. It is responsible for routing logistics. When an order is placed, this service calculates the geographical distance between the customer and various warehouses to select the most optimal dispatch location.

\subsection{Delivery Service}
Manages the assignment of delivery personnel and provides tracking endpoints. Go's lightweight goroutines make it exceptionally well-suited for tracking thousands of simultaneous active deliveries.

\subsection{Notification Service}
An asynchronous worker service. It listens for HTTP webhooks triggered by the Order Service and dispatches confirmation emails via an external SMTP server. Go ensures that SMTP latency does not block the main order flow.

\section{Database Layer}

\subsection{Schema Design}
Each service operates its own PostgreSQL schema. Migrations and schema creation are handled either via Spring Data JPA (Hibernate auto-ddl) or standalone \texttt{schema.sql} scripts mapped into the containers.

\subsection{Consistency and Reliability}
By avoiding a monolithic database, the "blast radius" of a database failure is minimized. An outage in the Delivery DB does not prevent users from browsing products or placing new orders.

\section{Docker Containerization}

\subsection{Service Containerization}
Every application component is containerized. Dockerfiles are standardized across the repository.

\subsection{BuildKit and Caching}
The CI pipeline leverages Docker BuildKit (\texttt{BUILDKIT\_INLINE\_CACHE=1}) to dramatically speed up build times by reusing cached layers from previous builds, saving crucial minutes during CI execution.

\section{Jenkins and CI/CD Automation}

\subsection{Overall CI/CD Architecture}
The system employs a fully declarative \texttt{Jenkinsfile}. Upon every Git push, Jenkins orchestrates a multi-stage pipeline: Checkout, Build, Test, Push to Registry, and Deploy.

\subsection{Sequential Builds and Resource Management}
To prevent out-of-memory errors on Jenkins worker nodes, resource-intensive Maven and Go builds are executed sequentially rather than concurrently.

\subsection{Automated Rollbacks}
A critical feature of the Jenkins pipeline is its \texttt{post \{ failure \}} block. If the deployment stage fails, or if health checks do not pass, Jenkins automatically triggers an Ansible rollback playbook (\texttt{rollback-k8s.yml}) to instantly revert the Kubernetes cluster to the previous stable image tag.

\section{Ansible Deployment Automation}

\subsection{Deployment Playbooks}
Ansible replaces shell scripts for deployment. The \texttt{deploy-k8s.yml} playbook connects to the Minikube cluster and injects dynamic configuration variables.

\subsection{Secret Management with Ansible Vault}
No secrets are stored in Git. Jenkins injects credentials into an encrypted \texttt{ansible-vault} file during the pipeline run. Ansible decrypts this file in memory and safely creates Kubernetes \texttt{Secret} manifests, applying them directly to the cluster.

\section{Kubernetes Orchestration}

\subsection{Role of Kubernetes in the System}
Kubernetes (Minikube) manages container lifecycle, networking, and scaling.

\subsection{Namespaces and Logical Isolation}
All microservices are deployed within a dedicated \texttt{smart-order} namespace to ensure they do not interfere with system-level pods.

\subsection{Service Discovery and Networking}
Kubernetes \texttt{Service} resources (ClusterIP) provide stable internal IP addresses and DNS names for the dynamic pods, allowing the API Gateway to reliably route traffic without hardcoding IP addresses.

\section{PLG Stack for Observability}

\subsection{Migration from ELK to PLG}
The project intentionally migrated away from Elasticsearch to Loki. Loki's index-free, label-based architecture requires significantly less RAM, preventing Minikube cluster instability while providing excellent log aggregation capabilities.

\subsection{Prometheus and Promtail}
Prometheus continuously scrapes system metrics (CPU, RAM). Promtail runs as a DaemonSet, capturing standard output from all Docker containers and shipping it to Loki.

\subsection{Grafana Unified Dashboards}
Grafana connects to both Prometheus and Loki, allowing developers to view request latency spikes and immediately correlate them with specific error logs in a single dashboard view.

\section{Testing Strategy}
Automated tests are enforced within the Jenkins pipeline. Spring Boot services use JUnit and Mockito; Go services utilize the native \texttt{go test} framework. The CI aborts immediately if any test fails, preventing broken code from reaching the registry.

\section{Innovative Solutions and Unique Approaches}

\subsection{Smart CI/CD with Differential Tags}
Every deployment is tagged with the Jenkins Build Number and the Git Commit Hash (e.g., \texttt{42-a1b2c3d}). This creates an immutable audit trail from production containers directly back to the exact code change in GitHub.

\subsection{Twin Service Benchmarking}
A unique architectural experiment within the project is the existence of the \texttt{warehouse-twin}. The warehouse routing logic was written in both Spring Boot and Go. This allows the team to perform live A/B benchmarking to compare JVM Garbage Collection pauses against Go's lightweight runtime under massive parallel load.

\subsection{Ansible-Driven Dynamic Secrets}
By combining Jenkins credential binding with Ansible Vault, the project achieves an enterprise-grade secret injection mechanism that is completely transparent to the developer yet entirely secure in the repository.
