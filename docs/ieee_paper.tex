\begin{abstract}
The selection of a runtime platform for cloud-native microservices has significant implications for system latency, resource consumption, and operational cost. This paper presents a rigorous, controlled comparative performance analysis between Java 21 (Spring Boot 4.0) and Go 1.25 (Gin 1.12) within a production-representative, polyglot Smart Order Fulfillment System. Common benchmarking confounds are neutralized: Docker containers are equalized at 1 CPU core and 768 MB RAM, JVM heap is constrained to 512 MB, database connection pools are identically capped at 50, and a seven-panel Grafana dashboard captures RSS memory, P99 GC pauses, CPU utilization, P99 HTTP latency, heap churn, DB connections, and concurrency. Under a rigorous 35-minute staged K6 ramp to 200 concurrent virtual users, Go achieves 21\% lower average latency for read-heavy cached lookups (511 \textmu s vs. 647 \textmu s) at identical throughput ($\approx$108 req/s), while Java delivers 2.48$\times$ higher throughput for write-heavy multi-service order orchestration (43.89 vs. 17.69 req/s). The write-heavy disparity is traced to HTTP client connection management: Java's OpenFeign pools TCP connections transparently while Go's per-request client instantiation compounds handshake overhead across three synchronous inter-service hops on the critical path. Grafana telemetry reveals Java G1GC P99 pause times reaching 60 ms at peak load with no equivalent in Go's concurrent collector, Java RSS consuming 64--192 MB versus Go's near-flat 8--16 MB, and Java threads peaking at 800 versus Go's 700 goroutines at a fraction of the memory cost. These findings demonstrate that framework-level abstractions can outweigh language-level characteristics, while Go's operational efficiency in memory, GC determinism, and CPU headroom provides compelling advantages for resource-constrained deployments.
\end{abstract}

\section{Introduction}

The microservices architectural pattern has become the dominant paradigm for cloud-native systems \cite{b1}. The choice of runtime has cascading effects on latency, memory, container density, and infrastructure cost. Java's JVM ecosystem offers mature frameworks like Spring Boot with extensive middleware abstractions \cite{b2}, while Go compiles to native binaries with goroutine-based concurrency and minimal runtime overhead \cite{b3}.

Prior comparative studies suffer from confounds: unequal resource allocation, differing drivers, inconsistent pool sizes, or load profiles that fail to account for JVM JIT warm-up \cite{b4}. This paper constructs a controlled environment within the \textit{Smart Order Fulfillment System (SSP)}, where both runtimes serve identical API contracts against shared schemas, subject to a seven-panel observability harness and a rigorous 35-minute load profile per service.

Our contributions are: (1) a \textbf{twin-service methodology} enabling direct A/B runtime comparison with identical business logic; (2) a \textbf{fairness-first harness} equalizing CPU, memory, connection pools, and instrumentation; (3) empirical results across \textbf{two workload archetypes} under a 35-minute staged ramp to 200 VUs; and (4) \textbf{GC pause, CPU, and RSS telemetry} quantifying operational runtime overhead beyond throughput and latency.

As Fig.~\ref{fig:architecture} and Table~\ref{fig:topology} illustrate, both stacks intentionally cross the Java/Go runtime boundary at exactly one point---the warehouse layer---ensuring that neither stack benefits from purely same-runtime communication. The Java-Led stack calls into the Go Warehouse (port 8084); the Go-Led stack calls into the Java Warehouse Twin (port 9084). This cross-runtime symmetry isolates the HTTP client behavior as the primary variable.

The critical asymmetry lies in \textit{how} each orchestrator makes these calls. Java's Spring Boot uses OpenFeign \texttt{@FeignClient} declarative interfaces (Listing~\ref{lst:feign}), which transparently manage a pool of persistent TCP connections with HTTP/1.1 keep-alive. The Go twin uses Go's \texttt{net/http} standard library but instantiates a new \texttt{http.Client} on every function invocation (Listing~\ref{lst:goclient}), forgoing connection reuse entirely \cite{b9}.

\begin{lstlisting}[language=Java, caption={Java OpenFeign client---connection pooling is implicit}, label={lst:feign}]
@FeignClient(name = "inventory-service",
  url = "${inventory.service.url}")
public interface InventoryClient {
    @GetMapping("/products/{id}")
    ProductDTO getProductById(@PathVariable UUID id);
}
\end{lstlisting}

\begin{lstlisting}[language=Go, caption={Go HTTP client---a new client per call, no reuse}, label={lst:goclient}]
func GetProductById(productID uuid.UUID) (*ProductDTO, error) {
    url := fmt.Sprintf("%s/products/%s",
        cfg.InventoryServiceURL, productID)
    // New client on every invocation: no pool, no keep-alive
    client := &http.Client{Timeout: 5 * time.Second}
    resp, err := client.Get(url)
    // ...
}
\end{lstlisting}

The contrast is deliberate: the Java listing requires zero transport-level code because the framework provides pooling as an invisible default, while the Go listing must explicitly configure an \texttt{http.Transport} to achieve the same behavior---a step omitted in the twin.

\subsection{Resource and Pool Equalization}

All six application containers are constrained identically via Docker Compose \texttt{deploy.resources.limits}: \textbf{1.0 CPU core, 768 MB RAM}. JVM flags are set to \texttt{-Xms256m -Xmx512m} with G1GC; Go operates with dynamic allocation. Both runtimes cap database connections at 50:

\textbf{Java (HikariCP):} \texttt{maximum-pool-size=50}, \texttt{minimum-idle=10}, \texttt{connection-timeout=30000}.

\textbf{Go (database/sql):} \texttt{SetMaxOpenConns(50)}, \texttt{SetMaxIdleConns(10)}, \texttt{SetConnMaxLifetime(30min)}.

Both runtimes achieved virtually identical throughput ($\approx$108 req/s), confirming the 1-second sleep makes the profile VU-bound rather than server-bound. Java outperformed Go by \textbf{2.48$\times$ in throughput} (43.89 vs. 17.69 req/s) and \textbf{3.49$\times$ in average latency} (1.47s vs. 5.13s). The error types are also revealing: Java's 10 errors were HTTP 500 (transient internal failures under peak load), while Go's 4 errors were HTTP 409 (stock exhaustion---a business logic outcome, not a failure). This means Go was both slower and ran out of inventory before Java, confirming Java processed significantly more successful transactions in the same duration.

This result is attributable to the HTTP client implementation asymmetry detailed in Section~II-B and illustrated in Listings~\ref{lst:feign}--\ref{lst:goclient}. As Table~\ref{fig:topology} shows, each \texttt{POST /orders} request triggers three synchronous inter-service calls on the critical path: an inventory price lookup (\texttt{GET}), a warehouse stock query (\texttt{GET}), and a warehouse stock deduction (\texttt{POST}). The notification dispatch, while also using an HTTP client, executes asynchronously and does not contribute to user-facing latency.

Java's OpenFeign reuses persistent TCP connections from its internal pool across all three hops. The Go twin, by contrast, instantiates a new \texttt{http.Client\{\}} for each call, requiring a full TCP three-way handshake (SYN $\rightarrow$ SYN-ACK $\rightarrow$ ACK) per hop. Under 200 concurrent VUs, the Go Order service attempts to rapidly open and close approximately $200 \times 3 = 600$ ephemeral TCP connections per request wave across two distinct destination ports simultaneously, saturating the Docker bridge network layer. Grafana confirms the resulting bottleneck: order-java P99 peaked at 2.26 ms (mean 0.239 ms) versus order-go-twin at 9.72 ms (mean 4.31 ms).

\subsection{Garbage Collection Behavior}

The P99 GC Pause panel provides direct evidence of JVM G1GC overhead absent in prior shorter tests. At idle, Java services exhibited pauses of approximately 10--20 ms. During the write-heavy phase (11:00--12:00 on the 3-hour dashboard), P99 pauses climbed to \textbf{60 ms} across all three Java services, decaying to $\approx$20 ms during the read-heavy phase (12:30--13:50) and approaching zero post-cooldown. The warehouse-java-twin exhibited the longest pauses, consistent with its Haversine computation generating additional short-lived allocations.

Go has no visible GC line at dashboard scale: its concurrent tri-color mark-and-sweep collector produces sub-millisecond pauses that are invisible at the millisecond axis. This confirms that Java's GC introduces \textbf{latency non-determinism} under load---every GC pause event correlates with a transient spike in the P99 HTTP latency panel---while Go's latency profile remains smooth throughout.

\subsection{CPU Utilization}

The CPU Rate panel reveals consistent behavioral differences across the full 2.5-hour test window. Java services exhibited utilization of approximately \textbf{20--40\% of the 1-core limit} under write-heavy load, with a characteristic sharp burst at the onset of each ramp phase consistent with HotSpot JIT compilation of hot code paths. After JIT stabilization, CPU settled to a lower sustained level---evidence that the 35-minute profile successfully captures post-JIT steady-state behavior, unlike shorter tests.

Go services processed equivalent workloads at \textbf{$<$5--10\% CPU}, retaining significant headroom throughout. The magnitude of Go's CPU efficiency advantage---roughly 4--8$\times$ under this workload---means Go containers can absorb substantially larger traffic spikes before triggering autoscaling in a Kubernetes HPA deployment.

\section{Discussion}

\subsection{Architectural Implications}

The results challenge a common assumption: that Go's compiled-binary nature delivers uniformly superior HTTP performance. \textbf{Framework-level abstractions can outweigh language-level advantages.} Java Spring Boot's OpenFeign client, with transparent connection pooling and keep-alive management, proved decisively superior to Go's per-request \texttt{http.Client} in multi-service orchestration. The 2.48$\times$ throughput advantage is entirely attributable to this framework behavior, not JVM superiority.

For read-heavy, cache-friendly workloads, Go's latency advantage narrowed from 38\% (in the prior 5-minute test) to \textbf{21\%} in the 35-minute profile. This convergence is significant: the longer test allowed Java's JIT compiler to fully optimize the hot cache lookup path, partially closing the latency gap. Java's lower maximum latency (10.27 ms vs. 12.74 ms) in the read workload further corroborates sustained JIT benefits, supporting the importance of JVM warm-up time in fair benchmarking.

\subsection{The HTTP Client Confound}

The Go order twin's deficit represents a threat to internal validity that must be explicitly acknowledged. As Listings~\ref{lst:feign} and~\ref{lst:goclient} demonstrate, the asymmetry is stark: Java's entire inter-service client is a 5-line declarative interface with connection pooling provided invisibly by the framework, while Go's client requires explicit transport configuration that was omitted in the twin implementation.

\subsubsection{Quantifying the TCP Handshake Penalty}

The per-request client pattern imposes a multiplicative penalty that scales with both concurrency and hop count. Each TCP three-way handshake adds one round-trip time (RTT) of latency. Within a Docker bridge network, intra-host RTT is typically $<$0.1 ms, but under 200 concurrent VUs each performing 3 synchronous hops, the Go Order service must establish approximately 600 new TCP connections per request wave. At the \texttt{Sustain} phase (200 VUs for 10 minutes at $\approx$17.7 req/s), this translates to approximately $17.7 \times 3 \approx 53$ TCP connection establishments per second sustained over 600 seconds---totalling over 31,000 ephemeral TCP connections during the sustain phase alone.

Each closed connection enters the \texttt{TIME\_WAIT} state for the kernel's \texttt{tcp\_fin\_timeout} period (typically 60 seconds on Linux), meaning up to $53 \times 60 = 3{,}180$ sockets may accumulate in \texttt{TIME\_WAIT} simultaneously on the Docker bridge interface. While this does not exhaust the 16-bit ephemeral port range ($\approx$28,000 ports), it creates measurable kernel socket-table overhead that Java's pooled connections entirely avoid.

Java's OpenFeign, by contrast, maintains a pool of persistent connections with HTTP/1.1 keep-alive. After the initial handshake during warm-up, subsequent requests reuse existing sockets with zero additional handshake cost. The 2.48$\times$ throughput advantage is thus not a JVM runtime benefit but a direct consequence of amortized connection setup cost.

\subsubsection{The Production Fix}

A production-grade Go implementation would declare a package-level shared client with an explicitly configured transport:

\begin{lstlisting}[language=Go, caption={Production-grade Go HTTP client with connection pooling}, label={lst:gofix}]
var sharedClient = &http.Client{
  Timeout: 5 * time.Second,
  Transport: &http.Transport{
    MaxIdleConns:        100,
    MaxIdleConnsPerHost: 50,
    IdleConnTimeout:     30 * time.Second,
  },
}
\end{lstlisting}

This single change would eliminate the per-request handshake penalty and is the idiomatic pattern recommended by Go's standard library documentation. The current confound therefore measures \textit{framework ergonomics and developer best-practice adherence}: Java's Spring Boot makes connection pooling the invisible default, while Go's standard library requires the developer to opt in. This distinction is itself a meaningful finding for engineering teams evaluating framework maturity.

\subsection{Operational Efficiency}

Go's 12--24$\times$ lower RSS footprint, $<$10\% CPU utilization versus Java's 20--40\%, and absence of GC pause non-determinism collectively define its operational advantage. In a Kubernetes deployment with 8 GB allocatable RAM, practical container density ratios favor Go by approximately 10$\times$ even within container memory ceilings. Go's lower CPU utilization defers HPA scale-out events, directly reducing per-node costs in cloud environments billed by core-hour. Cold-start time amplifies this: Go binaries reach full serving capacity in milliseconds versus Spring Boot's multi-second initialization, which also manifests as the CPU burst visible at each Java ramp-onset in the dashboard.

\subsection{Threats to Validity}

(1) Neon PostgreSQL's network latency may mask local computation differences. (2) Go's per-request HTTP client in the order service conflates framework maturity with runtime performance. (3) Results are specific to Spring Boot 4.0.2 and Gin 1.12.0. (4) The equalized pool size of 50, while methodologically correct, still produced 120--130 pending connections at peak load, confirming the bottleneck shifted to database processing capacity---a nuance that limits connection-pool metrics as isolated evidence.

\section{Conclusion}

This paper presented a controlled, 35-minute comparative benchmark of Java Spring Boot and Go Gin across read-heavy and write-heavy workloads at 200 concurrent users, within a fairness-first containerized environment. Seven Grafana panels provided multi-dimensional telemetry across throughput, latency, GC pauses, CPU utilization, RSS memory, DB connections, and concurrency.

Neither runtime is universally superior. Java achieved \textbf{2.48$\times$ higher throughput} in write-heavy multi-service orchestration---driven entirely by OpenFeign's implicit connection pooling, not JVM runtime superiority. Go demonstrated \textbf{21\% lower average latency} for cached reads, though this advantage narrowed versus shorter tests as Java's JIT compiled hot paths, underscoring the necessity of extended warm-up periods in fair JVM benchmarking.

Operationally, Go presents compelling advantages: a 12--24$\times$ lower RSS footprint, GC pauses below 1 ms versus Java's 60 ms at peak load, and CPU utilization of $<$10\% versus Java's 20--40\%---translating directly to higher container density, lower autoscaling frequency, and reduced infrastructure cost. Both runtimes achieved $<$0.01\% error rates at peak load, validating the robustness of containerized microservice deployments under equalized constraints.

The central finding is architectural: \textbf{the performance gap between Java and Go in write-heavy orchestration is a framework-maturity gap, not a language gap}. Future work will implement pooled HTTP clients in the Go order service to quantify the true runtime delta, extend analysis to GraalVM Native Image, evaluate HTTP/2 inter-service communication, and benchmark Kubernetes HPA behavior under production load patterns.
